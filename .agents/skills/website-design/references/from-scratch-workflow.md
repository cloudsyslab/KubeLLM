# Website phases and decision gates

Use this map for a new site or app, or a broad redesign. Adapt the number of passes to the actual brief; keep each pass moving toward one browser-visible decision. `$website-design` owns collaborative intent and judgment. `$website-design-build` owns the next explicitly started work pass. Neither automatically invokes the other.

## Brief the intent, then build the room

In reasoning mode, read the repository and product context first, then settle only what a rendered option cannot: audience, visitor or operator task, primary action, available proof/copy/assets, protected claims, product behavior, and practical constraints. Use `$grilling` for those questions one at a time, with recommendations, and focused `$discovery` fact checks when needed. Show visual questions as rendered boards; explore visual character in the room instead of interviewing for it.

Agree the room's scope: whether the baseline is explicitly locked or open; if open, the two or three distinct, reference-led directions and the representative page or core flow they will show; the sections still being designed after baseline selection; and the shared demo content or scripted scenario and states to compare. Reuse captured packs and include their lineage. Capture the specific pages a board needs during this mode, and commission a separate references pass when the room needs a broader shelf. A room never guesses at how a reference looks. After the user picks or mixes a direction, resolve it into one coherent baseline before designing section options on shared tokens. Save the scope using [Work handoff](work-handoff.md). A settled brief becomes `ready`; wait for `$website-design-build`, plus a fresh `$build-from-plan` when the pass works on a branch in an existing product.

## Separate work output from the next choice

| Explicit build pass | Deliverable at the review gate | Decision in the next explicit reasoning pass |
| --- | --- | --- |
| References/discovery | A varied high-signal visual shelf with exact source links, local packs, playable motion, original replay routes where captured, and honest evidence gaps | Which references should seed the room's options? |
| Options room, baseline round | Two or three strong, independently art-directed directions on the same representative page or core flow and content; each has its own coherent visual system and reference lineage. Skip only when the user explicitly locks the identity. | Pick a direction or name a mix to consolidate into one v0 baseline |
| Options room, section round | The whole working site or app on the chosen baseline, with two to five switchable options for every undecided section. These options share the chosen tokens, demo, and recommendations, with desktop and phone evidence. | Pick per section or name mixes; leave the rest for another round |
| Consolidation | Picks and mixes merged into finished sections, decided sections collapsed to their chosen design, open sections still switchable, with refreshed visible behavior and source lineage | Decide the remaining sections, ask for more options, or declare implementation readiness |
| Product implementation | The decided design and behavior in the actual site, with browser and technical verification | Accept the result or define a focused corrective pass |

Review useful evidence before commissioning more work. Do not force an extra research pass when existing references answer the question, or a new room for a small approved fix. Consolidation can take several rounds, each ending at a review gate, and finer changes later go through the same options-and-picks loop. A bounded pass may include the supporting research/capture/verification needed for its deliverable; it ends before the next user-owned choice or later product integration.

## Judge the whole component and visitor story

Connect arrival/promise, proof, understanding, differentiation, objections/process, and next action. Assess composition, type, spatial density, actual imagery/assets, section rhythm, motion timing/triggers, and responsive/interaction states together. Give each option enough depth to expose that system; small inert thumbnails are navigation rather than sufficient evidence.

Keep supplied content and label conceptual UI/copy. Preserve a strong 1:1 bias for selected source behavior. The builder's [Motion and fidelity guidance](../../website-design-build/references/motion-implementation.md) governs capture and reproduction. For a moving reference, collect playable unedited live evidence and test the original WACZ in replay when the sidebar supports it or the user has chosen a separate capture runtime for this task. Otherwise, retain the available sidebar evidence and mark recording/archive/replay coverage incomplete. Package validation, ReplayWeb receipt, replay behavior, and visual comparison are separate results; failed capture/replay and verifier disagreements stay explicit.

## Record selection, then prepare integration

As sections are decided, save the coherent design decisions: the baseline look, each pick or mix and how its pieces combine, hierarchy, type/spacing/color, page rhythm, assets, component behavior, motion, breakpoints, source lineage, and open fidelity gaps. Consolidation stays within the room until an implementation pass is separately understood and explicitly started.

Choose the production framework for the actual site, content/runtime needs, and deployment target. Current compatibility questions need primary-source discovery. A modern frontend preference calls for evaluating suitable current tools; a standalone room's stack does not predetermine that decision.

Picks and implementation readiness record decisions. Starting product implementation still requires `$website-design-build` with that scope, plus a fresh `$build-from-plan` in an existing product. Publishing/deployment is separately authorized. Finish every work pass at its review gate; the user can switch models before invoking `$website-design` for the next decision.
