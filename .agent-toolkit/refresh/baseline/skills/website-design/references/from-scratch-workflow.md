# Website phases and decision gates

Use this map for a new site or broad redesign. Adapt the number of passes to the actual brief; keep each pass moving toward one browser-visible decision. `$website-design` owns collaborative intent and judgment. `$website-design-build` owns the next explicitly started work pass. Neither automatically invokes the other.

## Intent, then a reference brief

In reasoning mode, establish the audience, visitor task, primary action, available proof/copy/assets, visual character, and practical constraints. Read the repository and existing product context first. Use `$grilling` for consequential questions one at a time, with recommendations, and focused `$discovery` fact checks when needed.

Agree what the reference run needs to establish: page story, hero/service demonstration, navigation/conversion, section rhythm, component behavior, responsive treatment, and motion. Save that scope using [Work handoff](work-handoff.md). A settled brief becomes `ready`; wait for `$website-design-build` before consolidated research or capture.

## Separate work output from the next choice

| Explicit build pass | Deliverable at the review gate | Decision in the next explicit reasoning pass |
| --- | --- | --- |
| References/discovery | A varied high-signal visual shelf with exact source links, local packs, playable motion, original replay routes where captured, and honest evidence gaps | Which references and page story should shape the directions? |
| Direction room | Three distinct, comparable directions against the same brief/content, full-size previews, real interaction/motion proofs, representative later sections, and mobile evidence | Select a direction or specify components to combine |
| Selected refinement | One reconciled composition with refreshed visible behavior and source lineage | What needs another refinement, or is the composition ready for implementation? |
| Product implementation | The accepted composition and behavior in the actual site, with browser and technical verification | Accept the result or define a focused corrective pass |

Review useful evidence before commissioning more work. Do not force an extra research pass when existing references answer the question, or three new directions for a small approved fix. A bounded pass may include the supporting research/capture/verification needed for its deliverable; it ends before the next user-owned choice or later product integration.

## Judge the whole component and visitor story

Connect arrival/promise, proof, understanding, differentiation, objections/process, and next action. Assess composition, type, spatial density, actual imagery/assets, section rhythm, motion timing/triggers, and responsive/interaction states together. Give each direction enough depth to expose that system; small inert thumbnails are navigation rather than sufficient evidence.

Keep supplied content and label conceptual UI/copy. Preserve a strong 1:1 bias for selected source behavior. The builder's [Motion and fidelity guidance](../../website-design-build/references/motion-implementation.md) governs capture and reproduction. For a moving reference, collect playable unedited live evidence and test the original WACZ in replay when the sidebar supports it or the user has chosen a separate capture runtime for this task. Otherwise, retain the available sidebar evidence and mark recording/archive/replay coverage incomplete. Package validation, ReplayWeb receipt, replay behavior, and visual comparison are separate results; failed capture/replay and verifier disagreements stay explicit.

## Record selection, then prepare integration

After a direction or component mix is accepted, save the coherent design decisions: hierarchy, type/spacing/color, page rhythm, assets, component behavior, motion, breakpoints, source lineage, and open fidelity gaps. Refinement stays within the room until an implementation pass is separately understood and explicitly started.

Choose the production framework for the actual site, content/runtime needs, and deployment target. Current compatibility questions need primary-source discovery. A modern frontend preference calls for evaluating suitable current tools; the disposable room does not predetermine that decision.

Direction approval and implementation readiness record decisions. Starting product implementation still requires `$website-design-build` with that scope. Publishing/deployment is separately authorized. Finish every work pass at its review gate; the user can switch models before invoking `$website-design` for the next decision.
